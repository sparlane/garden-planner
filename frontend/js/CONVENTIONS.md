# Frontend conventions

- Write new React components as function components with hooks. Convert existing class components opportunistically when touching them, not in a sweeping rewrite.
- Send API requests through the shared helpers in `utils.tsx`. They publish a global error alert by default and throw `ApiError` when a caller needs local recovery or field-level handling.
- Render decimal quantities through `formatQuantity` in `utils.tsx`, never by interpolating the raw value. Quantity columns are `DECIMAL(24, 9)` and the API serialises them zero-padded, so `{quantity}` renders `24.000000000`. The helper trims the padding losslessly and takes a fallback for null: `formatQuantity(inventory?.remaining_quantity, 'Unknown')`. Keep it operating on the string — parsing to a `number` reintroduces the float artifacts the decimal column exists to avoid. Money fields are covered by `formatMoney`, described in the next bullet.
- Render money through `formatMoney` in `utils.tsx`, never through `formatQuantity`: `formatMoney(breakdown.final_total, breakdown.currency_code, 'Unknown')`. Money columns are `DECIMAL(18, 4)` and serialise as `"1.0800"`, so `formatQuantity` would trim that to `1.08` correctly but `"1.1000"` to `1.1`, which reads as an incomplete price. `formatMoney` keeps two decimal places always, shows the third and fourth only when they carry a digit, and appends the currency code, so an amount and the currency it was recorded in never get separated. Like `formatQuantity` it works on the string and never parses to a `number`. An amount of `null` means the cost is genuinely unknown — a lot with no recorded unit cost — so pass a fallback that says so rather than letting it render as zero.
- Render a quantity that carries a unit through `formatMeasure` in `utils.tsx`: `formatMeasure(harvest.quantity, HARVEST_UNIT_LABELS[harvest.unit_code])`. It composes `formatQuantity` with the unit label, so a measured value and the unit it was measured in never get separated on their way to the screen. This matters most in yield reports, where count, mass, and volume totals sit in adjacent columns and a bare number would be ambiguous.
- Name a location by its `full_name`, not its `name`, wherever the reader is choosing between locations or being told where something is. The server builds it by putting the ancestors in front — `Greenhouse 1 / Bench A / Bay 2` — because a bare `Bay 2` is ambiguous across three greenhouses and a picker showing bare names cannot be used. `name` alone is right only inside a tree that already shows the ancestry, which is what `locations.tsx` does with `depth` and `inTreeOrder`.
- Draw garden geometry through `GardenCanvas` in `garden/canvas.tsx`, never by writing another SVG. It takes plain area, bed, row, and square data rather than fetching any, which is what lets the Gardens screen and the setup preview render the same picture — so what a gardener is shown before saving is what they get afterwards. Model coordinates grow upwards and SVG grows downwards, so anything placing its own rectangle has to flip y through `calculateSvgY`; using the component means never having to remember that.
- Expand a garden layout template through `expandTemplate` in `garden/templates.ts`. It is pure — no React, no fetching — and returns the rows or squares a chosen template stands for, with placements relative to the bed, which is where the server measures them from too. Post those children as one array through `createGardenRows`/`createGardenSquares`: the whole batch is one transaction, so a template that collides on its last square leaves nothing behind, and each row is checked against the ones before it.
- Check whether stock, costing, and traceability detail should be shown with `isAdvanced(workspace)` in `workspace_mode.ts`, never by comparing `workspace.mode` or `workspace.garden_experience` alone. A Nursery workspace is always Advanced regardless of its stored `garden_experience`, so a bare `garden_experience === 'advanced'` check silently under-shows detail to Nursery users; the helper is the one place that OR lives.
- Get Garden-mode wording for `ProductionBatch` from `plantings/batch_terms.ts` (`batchCodeLabel`, `batchStatusLabel(s)`, `batchListHeading`, `batchNavLabel`, and the create/choose/option helpers), never by writing a `workspace.mode === 'garden' ? … : …` ternary inline. The model, API, and route keep the word "batch" everywhere; only these functions decide when a screen should say "planting cycle" instead, so the two vocabularies cannot drift apart component by component.
- Turn a rejected write into per-field messages with `errorsByField` in `utils.tsx`, rather than reaching into `ApiError.body` again: `const fieldErrors = errorsByField(error)`, then `isInvalid={'name' in fieldErrors}` with a `<Form.Control.Feedback type="invalid">`. It returns `{}` for anything that is not DRF's `{field: [message]}` shape, because a network failure has already been published to the global alert and has no field to attach to. A message filed under `non_field_errors` belongs in an `Alert`, not against a control — that is what the server sends when no single field is the wrong one, such as two beds overlapping.
- Show every message a rejected write gave with `messagesByField` in `utils.tsx`, not by reaching into `ApiError.body`: `messagesByField(error).inventory_units` is the list, and `errorsByField` is the first of each field built on top of it. A write over many records answers with one message per record under the field that named them — a bench of forty pots refused because two of them already hold a fill says which two — and a form that showed only the first would send the operator back for the next one on every retry. Use `errorsByField` where a form has a control per field and one message under each is the whole story; use this where the field is a selection and the messages are about what is in it.
- Name a taxable supply document's state and a correction's reason through `documentStatusBadge` and `CORRECTION_LABELS` in `billing/documents.tsx`, never by writing the words inline. There are three document states and six correction reasons, they appear on the register, the order panel and the printed document, and a screen that invented its own wording for `part_credited` or `wrong_rate` would describe the same legal record two ways. The printable view itself is the one place a document is laid out: reuse `/billing/supply-documents/<pk>/print/` rather than assembling a second version of the page from the detail endpoint, because that payload is also what carries the required-information checklist.
- Total money in the browser with `sumMoney` in `utils.tsx`, never with `reduce` over `Number(...)`. Money columns are `DECIMAL(18, 4)` and the API serialises them as strings for the same reason the column exists: `0.1 + 0.2` is not `0.3` in binary floating point, so a total assembled with `Number` can differ from the figure the server stores from the very same inputs — and a preview that disagrees with what is about to be saved is worse than no preview. It sums scaled integers and returns a plain 4-decimal string, so the result goes straight into `formatMoney`.
- Record when a supplier was paid through `ReceiptSettlement` in `inventory/settlement.tsx`, never by posting to the settle action from a screen of your own. It takes a receipt id and its current paid date rather than a `StockReceipt`, because a seed packet reaches its receipt through provenance and never holds the document. The date decides which GST period claims the input tax under the payments and hybrid bases, so the same rules — no future date, null to clear, and the field-level rejection surfaced rather than a bare 400 — have to hold wherever it is entered from. It also owns the cache invalidation, which spans inventory, reports and seed packets because all three render the paid state.
- Render a reservation's remaining hold time through `formatHoldRemaining` in `utils.tsx`, not by formatting `expires_at` as a date: `formatHoldRemaining(allocation.expires_at)` gives `in 3 days` or `lapsed 2 hours ago`. The question an operator is asking of held stock is how long they have, and the sales order screen and the plant register both have to answer it the same way — the register's `reserved_until` is the same instant reached through the plant. A null means an open-ended hold that the expiry sweep (`sales/expiry.py`) never touches, so the fallback has to say that rather than render an empty cell that reads as "expires soon".
- Give a "when did this happen" field that defaults to now `useNowDatetimeInput` from `utils.tsx`, not `useState(localDatetimeInputValue())`: bind `value` and `change` to the `datetime-local` input, call `reset()` when the form reopens, and send `instant()`. The input only holds minutes and its default is read when the form opens, so an untouched default sent as shown lands before a pot fill the server opened a few seconds earlier, and a media application or a placement into that fill is refused until the clock reaches the next minute. `instant()` returns the moment it is called until the operator edits the field, and exactly what they typed after that. A field that sets a deadline or a planned time, like a work item's due window or a sale's hold expiry, does not need it, because nothing on the server is checked against it.
- Name a cohort loss cause through `LOSS_CAUSE_LABELS`, `RECORDABLE_LOSS_CAUSES` and `lossCauseLabel` in `plantings/loss_causes.ts`, never by writing `failed`/`lost`/`culled`/`donated` into a screen. The same five words appear on the cohort action form, the cohort history, the register filter and both loss-by-cause report summaries, and they are the cohort half of a vocabulary the server keeps aligned with the individual-plant lifecycle events in `plantings/loss.py` — a screen inventing its own wording would describe the same event two ways depending on whether the stock had identities. `RECORDABLE_LOSS_CAUSES` omits `unspecified` because the API rejects it on a new loss: it only ever describes losses recorded before a cause was required, which is why `LOSS_CAUSE_LABELS` still names it for history and totals.
- Name a block of anonymous stock's state through `COHORT_STATE_LABELS` in `plantings/cohort_terms.ts`, never by writing `growing`/`available`/`retained`/`depleted` into a screen. Two screens ask about it from opposite directions — the cohort register lists blocks by state, the batch screen reports how much of one crop is standing in each — and now that an order may commit to stock that is only growing, the state is what tells a grower whether a reservation is stock a picker can go and get or a promise they have to keep alive. Report `committed_forward_quantity` beside `reserved_quantity` wherever a cohort's reservations are shown, rather than folding the two together: the register, the cohort detail, the batch screen and the order screen all have to draw the same distinction, and a single "reserved" figure would answer "when can you deliver?" wrongly on exactly the stock the question is about.
- Say whether a germination count is finished through `GerminationStateBadge`, `GerminationSummary` and `formatGerminationRate` in `plantings/germination.tsx`, never by rendering `observed_count` or `rate` on their own. An open sowing's count can still rise, so the same three numbers mean two different things depending on `provisional`, and the tray screen, the batch screen and the sowing list all have to draw that distinction the same way — a screen showing a bare count invites a re-sow decision made against a figure that was never final. `formatGerminationRate` takes the server's fixed six-decimal string rather than a number, for the same reason `formatQuantity` does.
- Work out where a label lands on its sheet with `sheetLayout` in `labels/sheet.ts`, never by dividing a page width by a label width in a component. Label stock is not symmetrical — LC24 runs its labels to both paper edges with a 4.5mm bar only at the top, and sheets commonly part their columns while butting their rows together — so the four figures that place the first label are separate measurements, with `margin_top_mm` and `row_gap_mm` falling back to `margin_mm` and `gap_mm` for stock that really is symmetrical. Two things read the answer and they must not disagree: `TemplateForm` tells a designer "3 across × 8 down", and `PrintArea` prints that many. `PrintArea` puts the sheet's bars on an `@page` margin rather than as padding inside the grid, because padding indents only the first page while a margin box repeats on every one; and it lays out a fixed `repeat(N, width)` rather than `auto-fill`, so a page narrowed by a printer's own margin setting overflows visibly instead of quietly printing one column fewer with every label of it on the wrong gum.
- Add a print template through `TemplateForm` in `labels/template_form.tsx`, never by posting to `/labels/templates/` from a form of your own. Designing a template is measuring a sheet, so the form asks for the sheet and says what it works out to before anything is saved — and it only ever adds one: the built-ins refuse every edit but retirement, and a template already printed against has to keep its geometry or a reprint lands somewhere the first print did not. A preset in it is a claim about somebody's physical paper, so put one there only when the arithmetic closes against a real sheet, the way LC24's three 70mm labels close against the 210mm of A4; a guessed preset wastes the box rather than merely being inconvenient. Roll and single templates state the label alone and are not asked for a page, which is the same distinction `sheetLayout` draws.
- Name the kind of record a label is stuck to through `labelTargetLabel` and `LABEL_TARGET_TYPES` in `labels/target_types.ts`, never by rendering `target_type` or writing `inventoryunit` into a screen. The value is a Django content type's model name — it is what `/labels/identities/` filters on and what it sends back on every row — so a screen printing it raw tells a grower their pots are `inventoryunit`s, and a second screen inventing nicer wording of its own would name one kind of record two ways. Narrow the list through `getLabelIdentities`, which takes the whole query — `targetType`, `objectId`, `page` — and keys it with `queryKeys.labels.identities(query)`. Every field narrows on the server: the comparison is made against the content type behind a generic foreign key rather than anything the row carries, and the list is paged, so a browser filtering what it was sent would be filtering one arbitrary hundred. That is also why a screen wanting one record's code asks for it by `objectId` instead of searching a fetched list, the way the numbered container page does — a scan of page one finds nothing once a workspace has numbered more pots than fit on it. One cache entry serving two different queries would make what the unit detail page shows depend on what somebody last chose on the Labels screen. The response is a page rather than an array: `results` and `count`, plus `target_types`, which counts the printable labels of each kind across the whole workspace rather than the page or the current filter, because it is what the type picker is built from — and that fifth key is also what stops `unwrapPaginatedResponse` handing the caller page one as a bare list. Selections are identities, not rows, so they outlive both the filter and the page they were made on — printing a sheet of pots and the plants going into them is one job — which means a screen has to say how many chosen labels are not currently shown rather than let the print button's count disagree with the table.
- Give inventory units their asset codes through `NumberedUnitsPanel` in `inventory/individualization.tsx`, never by posting to the individualize action from a screen of your own. The count goes against one lot at one place rather than against the item, because pots from two deliveries cost different amounts and a numbered container carries the cost of the lot it came out of — an item-wide control would have to guess which. It owns the cache invalidation, which spans inventory and reports because numbering writes no stock movement: on-hand and valuation are unchanged and only the split between loose and numbered moves, so a screen that invalidated the ledger instead would refetch everything and still show the old split. Numbering is one-way once a container has moved, been labelled or been promised, which is why the panel says so before the operator commits rather than failing afterwards.
- Name the place a plant is standing through `placementLabel` and `PLACEMENT_LABELS` in `plantings/placements.ts`, never by writing `seed_tray_cell` or `container_unit` into a screen. The plant's own history, the batch screen, the register and the bulk-move review all name a placement, and the four kinds are not symmetrical: a tray cell and a garden square are drawn on screen and are found by the row they came from, while a numbered pot is found by the asset code printed on it — which is why `placementLabel` prefers `container_unit_code` and why the register's location cell puts the kind of place under the code rather than beside it. A pot with no code to hand still names itself, so a caller carrying only the type gets the bare label rather than `#undefined`.
- Offer a numbered pot as a destination through `useNumberedPotDestinations` and `potOptionLabel` in `plantings/pot_destinations.tsx`, never by querying the pot catalog and its units from a screen. A pot is chosen in two steps — the catalog item, then one of its pots — because the pots of one item are what an operator is choosing between and every numbered container in the nursery is not, the same shape as a tray and then a cell. What the two lists leave out is the part a second screen would get wrong silently: only `mixed` tracking items have pots with an identity to stand a plant in, and only units that are `active` **and** `available` are still in the nursery, so filtering on `active` alone would offer pots that have been sold. The hook keys the catalog by its filters rather than by the caller, so the bulk panel's repot picker shares the one entry, and the label puts the pot’s number first, then the code printed on it — the number is what the pot is called on its own inventory page and in its movement history, so a pot chosen here can be followed there without reading the code back off the container — then where the pot is standing, then whether a plant is already in it — a pot in use is still offered, because several plants legitimately share one the way a multigerm cell holds several seedlings. A screen that has just moved a plant into a pot revalidates `queryKeys.inventory.all`: standing a plant in a pot is what puts that pot in use, and the next plant would otherwise be offered it as though it were empty. Put `PotCodeField` above those two pickers wherever they appear: a nursery numbers more pots of one item than a dropdown can usefully hold, and the operator is holding the one they mean. It asks `/labels/resolve/` first, which is both what a QR scan pastes in and the only thing that knows a code has been replaced or belongs to another workspace, and falls back to the unit's own asset code — the identity the pickers display and the container page prints — so either code a pot answers to finds it. It reports what it found rather than selecting silently, because a numbered seed tray carries a label too and the placement rules check only that a container is individually numbered: nothing below the browser would stop a tray's code from standing a plant "in" the tray, whose plants are described by their cells. That check is the item list the hook returns, which is why the field takes it rather than fetching its own. A run of digits typed into it is a pot's number rather than a code: a number is the pot's own identity — `pk`, issued once, never reused, unique across the nursery — while both codes carry a prefix, and the asset-code filter matches on a fragment, so `81` left to the code path would quietly answer with every pot with 81 in its hex. `potOptionLabel` puts that number first for the same reason: it is what is written on a bench card and read off a pot, and the codes are opaque by design.
- Name a cost layer's input through `costSourceLabel` and `COST_SOURCE_LABELS` in `plantings/cost_sources.ts`, never by writing `application_line` or `container_unit` into a screen. The batch breakdown and the plant breakdown both list layers, and a screen inventing its own wording would describe the same input two ways depending on which page you were reading. `costSourceLabel` takes the whole layer rather than the source type because a container names the pot that left with the plant — the thing a grower can point at — while the lot behind it still holds the rest of the box.
- Show a planning assumption against what happened through `AssumptionVariancePanel` and `ReviseAssumptionForm` in `plantings/assumption_variance.tsx`, never by rendering an observed figure on its own. An assumed germination rate and an observed one are the same kind of number until something on the screen says which is which and how much evidence is behind it — three batches is not a season — so the panel always carries the sample count, the divergence badge, and what was deliberately left out: sowings still germinating, tray fills shared with another variety, and losses recorded with no stage observation standing. `ReviseAssumptionForm` is the only way to write the next version: it arrives pre-filled from the server's draft and labels every field as observed or kept, because an assumption is a commercial judgement about next season rather than an average of the last one, and a screen that saved the observed value on its own would be tuning it for the grower. The revision endpoint owns closing the previous version and copying its stages and inputs, so never post a new assumption to the collection to replace an existing one.
- Show what happened to a plant through `PlantTimeline` in `plantings/timeline.tsx`, never by assembling a history of your own from the lifecycle events, the nursery observations, the health cases and the order allocations. Those four are separate append-only records with separate owners, and they stay separate — the component reads the server's `specificplants/<pk>/timeline/` projection, which interleaves them under one stated ordering rule and pages the result. It renders the `label` the server sends rather than mapping `kind` to words of its own, so the timeline cannot describe a fact differently from the per-source screen it also appears on; only `SOURCE_LABELS` is named here, because which of the four histories a line came from is the one thing no source can say about itself. A corrected entry is shown struck through rather than dropped: all four sources correct by appending, and somebody investigating a failure has to see what the operator was looking at when they acted. The per-source cards stay on the plant screen beside it — an operator asking only what a plant was graded should not have to read the rest.
- Build a catalog picker's options with `activeChoices` in `catalog.tsx`, and never map the fetched list straight into `<option>`s: `activeChoices(varieties, draft.variety)`. Families, plants, varieties, suppliers, seed catalog entries, tray models, expense categories and the coded usage settings (growth stages, plant grades, health evidence types, health diagnoses) are retired rather than deleted, and their collections keep returning the retired ones because the same list is what names the entry an old planting, harvest or receipt points at — so a bare `.map` offers a gardener the very typo they retired, and the server then rejects the write. The second argument is the value the record being edited already holds: it stays in the list, because saving an unrelated correction must not silently repoint a record at something else. A _filter_ dropdown is the exception and takes the whole list, since narrowing a register to a retired variety is how somebody reads its history. `RetireButton`, `RetiredBadge` and `retiredRowClass` are the other half, for the screens that maintain the catalog itself: retirement is refused while something active still hangs off the record, and the refusal names what is in the way, so show it against the table rather than leaving it to the global alert.
- Merge a duplicate catalog record through `MergeDialog` in `catalog.tsx`, never by posting to the merge action from a screen of your own. Every mergeable collection shares one merge contract on the server, so the dialog takes the collection path — `/plants/variety/`, `/supplies/supplier/`, `/plantings/growth-stages/`, `/health/diagnoses/`, `/purchasing/expense-categories/` — rather than being written out once per screen. It previews before it commits, because a merge is the one catalog correction that moves records the operator is not looking at: choosing a survivor asks the server what would move onto it and what stands in the way, and the `Merge` button stays disabled while there are blockers. Build `choices` with `mergeChoices`, which drops the retired records and the record being merged away, and narrow what you hand it to the records filed in the same place first, the way the Plants screen does with a variety's plant and the health setup screen does with a diagnosis's category — the server refuses a merge that would refile a record as a reclassification, and a picker offering one makes that refusal the operator's problem rather than the screen's. What files a record is not always another record: a diagnosis is a pest or a disease, and neither is something anybody can retire. `MergedIntoNote` is the other half, for the row the duplicate leaves behind: it is retired rather than deleted and points at where it went, so a reader who searches for the old name still finds the trail.
- Correct a catalog record through `CorrectionDialog` in `catalog.tsx`, never by PATCHing the collection from a form of your own. An operator fixing a wrong entry should not have to know whether they are owed an edit or a replacement, so the dialog asks the server: `identity_locked` says whether posted stock has frozen the fields named in `identity_fields`, and a change to one of those saves a new record instead of rewriting this one. It says which is about to happen before the button is pressed, because the two leave the catalog looking very different afterwards — a replacement retires the old entry and starts a second one with its own inventory item, and everything already received stays on the old one. Own the form state and pass `original` and `values`; the dialog sends only the difference, because the server carries the rest of the record over and a screen posting the whole thing would overwrite fields it has no control for. The children callback is given `replacing` alongside the field errors, so a form can say something that only holds on the replacement path — a tray model's successor needing a name of its own, because the model it supersedes keeps the one its trays were received under — without asking the server the same question a second time. `ReplacedByNote` is the other half, for the row the superseded entry leaves behind, and reads as the replacement counterpart of `MergedIntoNote`.
- Say where a catalog record came from with `ReferenceBadge` and `referenceFigureClass` in `catalog.tsx`, and never work it out in the browser by comparing against a copy of the starter set. The server sends `reference_source` — blank on a record the gardener made — and `reference_fields`, the figures still saying exactly what that set supplied; it reads the second by comparison rather than storing it, so editing a figure is what makes it the gardener's and there is nothing for a screen to set. Pass the field name the API uses (`referenceFigureClass(plant, 'maturity_days_min')`) and put the class on the cell, so a figure printed for somebody else's climate reads more quietly than one measured in this garden. A range spanning two fields is marked on its `_min`, because the set supplies both or neither. Offer `installStarterCrops` whether or not the catalog is empty: installing twice creates nothing the second time, adopts a crop the gardener already typed rather than duplicating it, and leaves alone every figure they have measured and every record they have retired. `ReferenceBadge` shows the set's own name rather than a fixed word, because a catalog can arrive from a garden club or another garden as readily as from the set that ships in the box, and which one a record came from is the half worth reading.
- Search a catalog through `CatalogSearch` in `catalog.tsx` and `searchedKey` in `query.ts`, never by filtering the fetched list in the browser. The comparison is the server's — the normalized form of a name, the same one the duplicate warning makes, so a catalog cannot say two names mean the same thing in one box and not in the other — and varieties and seed catalog entries are paginated, so a browser-side filter would also be narrowing only the first hundred records it happened to be sent. The control holds what is typed and reports only what settles, so pass a state setter as `onSearch` and put the term into the query key with `searchedKey`: a searched list is a different list, and one cache entry serving both would make what a picker on another screen offers depend on what somebody last typed here. Keep the unsearched query alongside it and read the rows from the searched one — the pickers, the merge choices and the `Merged into`/`Replaced by` lookups all have to reach records the search is deliberately hiding. A blank search shares the unsearched key, so a screen nobody has typed into costs exactly what it did before. One term is sent to every collection a hierarchical screen shows, the way the Plants screen sends it to families, plants and varieties: a record is found by its own name and by every name above and below it, so what comes back still reads as a tree.
- Warn about a duplicate catalog record through `DuplicateWarning` in `catalog.tsx`, never by scanning the fetched collection with a `.find` of your own. The comparison is on a normalized form — case, punctuation, spacing and a trailing plural are how one name gets typed twice — and it allows an edit for every four letters, so a browser-side `===` would miss `Tomatoe` next to `Tomato`, which is the duplicate the whole feature exists for. Pass `scope` with everywhere a duplicate has to be filed too — the parents it hangs off (`{ plant: Number(plant) }` for a variety) and any value it is grouped under that is not a record at all (`{ category }` for a health diagnosis): the server answers within that or refuses, because two records are interchangeable only where a merge would allow it, and a warning naming a record from another crop, or from another diagnosis category, would offer a merge that then gets refused as a reclassification. Pass `exclude` when a form is correcting an existing record, which is never a duplicate of itself, and `field` when the collection names itself something other than `name` — a tray model uses `identifier`. A flat catalog with nothing filing it passes no `scope` at all, the way the Nursery growth setup screen does for stages and grades and the Purchasing screen does for expense categories. Leave `name` out altogether for a collection with no name typed on it: a seed catalog entry is one supplier's variety and no more, so the scope is the whole question and the warning appears as soon as both pickers are set. That is the collection it matters most on, because seed entries do not merge — two of them split one seed's stock across two inventory items and nothing can join them afterwards — so on the Seeds screen give the check the stand-in supplier (`is_system_default`) when none is named, or a Basic Garden entry goes unchecked for having no supplier typed on it. It renders nothing when there is nothing to say and warns rather than blocks, so put it under the last control it depends on and leave the save button alone: these catalogs carry no unique constraint on a name on purpose, and two suppliers really can trade under one.
- Never put a coded usage setting's `code` on a form after it has been created — show it, the way `growth_catalogs.tsx` and `health_catalogs.tsx` do with a `<code>` cell, and leave the editing to its name. A growth stage, a plant grade, a health evidence type and a health diagnosis carry a stable code as well as a name, and the code is the handle everything else holds the record by: `plantings/signals.py` and `health/signals.py` re-find the settings they seed by code every time a workspace is saved. So the server refuses to re-cut one and names the correction it is owed instead — add the setting under the code you want and merge this one into it — and a code somebody has already used is refused naming the setting that holds it, because a code already taken is not a resemblance to warn about but exactly the record the operator was looking for. Read alongside `CorrectionDialog`, the two are the same rule from opposite ends: a seed entry's supplier is frozen by what a packet was received as and correcting it starts a second entry, while a setting's code is frozen by what names it and correcting it merges into one.
- Keep the packet a sowing already names in any picker that corrects that sowing, the way `SowingCorrectionPanel` in `planting.tsx` does: it puts the sown-from packet back at the head of the options when the usable list has dropped it, looking it up in the every-state options `indexPacketOptions` builds. `/seeds/packets/` deliberately omits a packet once it is empty, because no new sowing should be recorded against one — but the packet a sowing came from is usually empty by the time anybody corrects that sowing, so a picker built from the usable list alone opens blank and reads as though nothing was sown. This is the seed-packet half of what `activeChoices` states for retired catalog records. The two lists are separate endpoints and take separate query keys: `queryKeys.seeds.packets.usable` for `/seeds/packets/` and `queryKeys.seeds.packets.everyState` for `/seeds/packets/all/`. Caching both under one key would make which packets a screen offers depend on which screen was opened first.
- Name a crop's planning figures through `CULTIVATION_FIGURES` in `plants/cultivation.tsx`, and read a variety's through the server's `effective` block with `effectiveFigure` and `EffectiveFigureCell` — never by rendering `variety.spacing` on its own. A blank figure on a variety is not one nobody has recorded: `plants/metadata.py` reads it through to the crop everywhere a sowing date, a maturity date or a projected task is worked out, so a bare `—` in a variety's cell names the one thing the system is not doing with it. The block says, per figure, the value in force and whether it is the variety's own, and that second half is what a browser cannot work out for itself — a blank and an override that happens to equal the crop's figure look identical until the crop is next corrected, and only then do they part company. The figures live in one list because four things read them: the catalog table's headings, its editor cells, and both detail pages. A range is one figure with two boxes rather than two figures — a reference set supplies both halves or neither and a gardener leaves the pair alone together — so `figureIsSet` and `figureText` take the whole figure, and anything counting what a record states has to count a range once. `CropFigureNote` is the guidance under a variety's box and `InheritingVarietiesNote` is the same sentence read from the crop's end; both belong under the control the figure is typed into, because a blank box is the one control on a catalog screen whose meaning is not written on it.
- Open a crop catalog record's own page at `/plants/family/:familyId`, `/plants/plant/:plantId` or `/plants/variety/:varietyId` in `plants/detail.tsx`, and link a name to it rather than adding a second way to open the hierarchical screen's row editor. The page reads the record by its own id — `getPlantVariety` under `queryKeys.plants.variety(pk)` — rather than picking it out of a collection, because varieties are paginated and the record somebody has navigated to need not be on the page the collection last cached; a crop's own varieties come from `getCropVarieties`, which is `/plants/variety/?plant=`, for the same reason. What the route is for is the room to say things a row cannot: which figure a variety is planned by and whose it is, and how many varieties of a crop are planned by the figure being corrected. It carries the record's corrections too — retire, merge, the duplicate warning under the name — because a gardener who has arrived at the wrong entry has arrived at the place to fix it, and a page that could only show it would send them back to the table to act.
- Carry a crop catalog between gardens with `ReferenceSetControls` in `catalog.tsx`, never by writing the download or the file input again. Export and import are one document and one route — `/plants/reference-set/` — so what a garden writes out is exactly what an import accepts, and the component only reads the file and hands it over whole: the server decides what a set may say, adopts a name the gardener already typed rather than duplicating it, and leaves alone every figure they have measured and every record they have retired. It exports through the authenticated JSON helper and downloads a blob rather than pointing an anchor at the route, which the browser would fetch without credentials. Everything in an arriving document becomes reference data in the receiving catalog, however hard won it was in the garden it came from, so a screen must never present an imported figure as one measured here — that is what `ReferenceBadge` and `referenceFigureClass` are already saying. Pass `describe` a summary of what the catalog now holds rather than of what changed: installing a set twice is meant to be uneventful, and a screen that said nothing the second time would read as a failure.
- Let an operator type at a picker that names one record out of many — a tray, a garden square, a cell, a pot, a packet — by giving it `Select` from `react-select` and reading the choice back with `selectOptionToPk` in `utils.tsx`, rather than a bare `<select>`. A nursery holds more of each of those than a dropdown can be scrolled through, and the operator already knows the one they mean, so the option label is what has to be typeable: react-select matches anywhere in the label, which is why these labels carry every identity a record answers to — a tray's printed asset code and inventory unit id beside its tray number, a pot's number beside its code, a cell's coordinates — instead of the one a native dropdown's first-letter typeahead could reach. Read the choice back through `selectOptionToPk` and never through `Number(option.value)`: react-select reports a cleared control as `null` and an option with an empty value as `undefined`, and a screen that handles only one of them posts `NaN` as the place it is putting a plant. The exception is a control whose options are a fixed handful of kinds rather than records — the move form's own `Move to:` is still a plain `<select>` — because there is nothing there to search for.
- Fill a run of numbered pots through `NumberedPotFills` in `inventory/numbered_fills.tsx`, never by posting the open action once per pot from a loop of your own. Each pot still gets its own fill, because a numbered pot owns its media history and its cost, but the claim over them is one request: the server locks every pot before writing the first fill, so a bench is either filled or refused with the pots that stopped it named, and a browser loop would leave half a bench filled with nothing to say where it stopped. The pots are named by number and by range, resolved against the server rather than against a fetched list — an item's pots outrun any page, and a screen that filled the first hundred of `81-500` would be filling pots nobody chose — and the range is asked for with `page_size` so a wide one comes back whole. What it checks in the browser is only what saves a refused round trip: a pot that is not on hand, or already holding a plant, is left off the bench with the reason said out loud. The server enforces all of it again under the locks, which is what makes it true.
- Pot a selection of plants on through `RepotRunForm` in `plantings/repot_run.tsx`, never by posting the move action once per plant from a loop of your own. A pot holds one plant, so a repotting is not the register's bulk move — that sends every selected plant to one place, which is what a bench or a garden square is — and it is not a move each either: the server takes every plant and pot lock before the first move, so a tray either empties onto the bench or stays as it was, while a browser loop would leave half a tray potted with nothing to say where it stopped. The form is the pairing table, and the pairing is positional: pots are paired with the selection in the order the screen lists it, so a range typed as `81-88` lands on the cells in the order the grid draws them. A pot that is not on hand, not a pot, or already in the run is left out with the reason said out loud, and a pot that is already holding a plant is paired with the label saying so, because several plants legitimately share one.
- Read a typed run of unit numbers through `parseBenchNumbers`, `rangeNumbers` and `numberList` in `inventory/bench_numbers.ts`, never with a regex of your own.
